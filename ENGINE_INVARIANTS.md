# Engine Invariants — the athlete-protection contract

The training engine's job is to train Rob **according to the science**, aggressively but safely. The failure mode that matters most is not a crash — it's a *silent* bug that quietly trains him according to the bug instead of the evidence (a stray rest day, a frozen muscle, a mis-fitted threshold). This file is the contract that prevents that class of bug from recurring. Every invariant here is enforced by an executable test in [`backend/tests/test_engine_invariants.py`](backend/tests/test_engine_invariants.py). If one fails, a change has re-opened a hole that once held the athlete back — **read the invariant before "fixing" the test.**

Origin: the 2026-07-03 soundness audit (four parallel deep-dives, each finding verified against source + live data before it was trusted). Each invariant below maps to a real defect that audit found and fixed.

## The invariants

1. **The ACWR band-fitter measures on the same window the live gate scores against.** `self_learning._historical_weekly_acwr` and `metrics._arm_acwr` must use the identical uncoupled window (acute = 7 days `[ws, ws+7)`, chronic = the contiguous 21 days before it `[ws-21, ws)`, each a per-day mean). *Why:* a personalized percentile band is only meaningful on the scale it is applied against; the audit found the fitter on a 28-day chronic window while the gate used 21-day, biasing every personal band.

2. **A measurably progressing muscle is never frozen by the confidence shrink.** For `perf ≥ 4`, recovered, below MRV, `_decide` returns `delta ≥ 1` at *any* confidence. *Why:* confidence caps ~0.34 by design and was rounding every add to zero — glutes (emphasis muscle, PRs for 8 weeks) was pinned at its grow-floor. Progress is an outcome signal; the shrink only governs *speculative* adds.

3. **The progression floor does not become a free ramp.** A muscle with no outcome signal (`perf is None`) on thin, low-confidence data still climbs only to its MEV floor, never above. Invariant 2 must not over-loosen into invariant 3's territory.

4. **No movement slips past its recovery gate.** Exercise classification never puts a pull/hinge pattern into `push` (it would pass a pull-rested day), and posterior-chain hinges (rack pull, pull-through, back extension, reverse hyper, KB swing) never fall through to `other`. `"Upright Row"` is the one deliberate row→push exception.

5. **A green day permits true top sets.** `load_cap_pct` is monotonic (`rest < low < moderate < high`) and `high ≥ 100%` of e1RM. An unset intensity must not silently fall through to a hard cap. *Why:* a silent load cap below e1RM on a green day is the "treated like a fragile 40-year-old" failure in load form.

6. **A progression-capping personal band may only loosen the population default, never tighten below it — and if a band can only ever loosen, fitting it is not worth pretending it's active.** Personal MEV is floor-only against population, enforced the same way invariant 3 is. Resistance ACWR (REST/LOW/MOD) is NOT fitted at all (as of the 2026-07 remediation): applying it floor-only meant a personal fit — a percentile of Rob's own load — sat below the population injury ceiling by construction, so `max(personal, population)` provably always resolved to population. It was computed, persisted, and reported as "personal (fitted)" while changing nothing; `self_learning.fit_acwr_bands` now only fits conditioning. *Why:* Rob's thin, noise-dominated N=1 history must never make a growth gate stricter than the population floor — the anti-progression trap — and a band that can only ever be floored isn't worth the ceremony of fitting it. Enforced end-to-end by `test_resistance_acwr_personal_bands_never_reach_the_gate`: absurdly tight resistance values written directly into `personal_acwr_bands` must not move `_gates`' thresholds off population.

   This floor-only philosophy also covers the **derived conditioning leg-HOLD threshold** (`metrics.personalized_cond_thresholds`, 2026-07-23 remediation). The hard `forbid_legs` bound is legitimately sample-gated tighten/free-loosen — it's the injury bound. But the graded `hold` was derived as `forbid − 0.3` with no floor of its own, so a well-sampled tightened `forbid` silently dragged `hold` down too even though the hold is a *volume-programming* decision, not an injury bound. With Rob's live fit (`forbid=1.53`, 37 weeks) this produced `hold=1.23` — a leg-volume hold active on ~40% of days for an athlete carrying real pickleball conditioning load, exactly the invariant-6 anti-progression trap in hold form. `hold` is now `max(forbid − 0.3, COND_ACWR_HOLD_LEGS)` (nudged inside `forbid` if a tight fit would otherwise collide with it) — it may still loosen below population when `forbid` loosens, it just never tightens below the population 1.5 floor. Enforced by `test_personalized_cond_thresholds_hold_never_tightens_below_population`, `_hold_stays_inside_a_tight_forbid`, `_hold_still_loosens_with_forbid` (test_gates.py) and `test_weekly_prescription_leg_hold_never_tighter_than_population` (test_autoregulation.py).

   The `forbid_legs` FIT itself (not just the derived hold) got a second floor-only-style guard on 2026-07-23 (Phase C): **a personal tighten below the population `COND_ACWR_FORBID_LEGS` (1.8) requires outcome evidence, not just a percentile.** `self_learning.fit_acwr_bands` is a raw P80 of Rob's own weekly conditioning-ACWR distribution — it will ALWAYS want to tighten (his own busiest 20% of weeks are definitionally above his own P80), with zero reference to whether those weeks actually preceded worse outcomes. Verified against the live DB: the persisted `forbid_legs=1.53` was entirely the `_COND_TIGHTEN_FLOOR_FACTOR` hard floor (0.85 × 1.8), not the raw fit (P80=1.21); comparing next-week recovery score and perf score for weeks above vs. below either candidate showed **no adverse signal** — recovery and perf were, if anything, slightly better after high-conditioning weeks. `self_learning.persist_acwr_bands` now calls `_acwr_outcome_supported` before attempting any tighten: it requires ≥5 observable high-ACWR weeks AND both next-week recovery (≥3.0 pts) AND next-week perf (≥0.15) to read worse on the high side — a single noisy n-of-1 metric can't shackle training alone. Unsupported → the population threshold (1.8) is persisted instead, with the fit's rejected value and deltas logged. Loosening (fit landing above population) is untouched — it never needed a floor. *Why:* an evidence-free percentile tighten is a circularity ("busy weeks are dangerous because they're busy"), not a personalization, and is exactly invariant 6's anti-progression trap wearing a different hat. Enforced by `test_persist_acwr_bands_unsupported_tighten_falls_back_to_population`, `test_persist_acwr_bands_supported_tighten_still_goes_through_clamp`, `test_acwr_outcome_supported_true_when_both_signals_worse`, `_false_with_too_few_high_weeks`, `_false_when_signals_disagree` (test_self_learning.py).

7. **Conditioning interference never freezes an EMPHASIS lower-body muscle below MEV.** The `leg_interference` hold (`weekly_prescription`, cond. ACWR > 1.5) holds quads/hams/adductors in place — correct, they absorb the eccentric court load — but an emphasis lower-body muscle (glutes) still floors at MEV. *Why:* the hold was checked before the MEV-floor branch, so glutes (emphasis, `perf=None`, thin data, `cur=0`) sat at 0 for every week cond. ACWR > 1.5 — i.e. most weeks, given 1000+ min/mo of pickleball — the exact silent under-train of a lagging priority muscle that invariant 3 forbids. Non-emphasis legs still hold; the climb to MEV is rate-limited to +2/wk so it eases in while sport volume is high. Enforced by `test_conditioning_interference_never_freezes_emphasis_below_mev`.

8. **A sub-meaningful training dose never locks a muscle out, and a distributed full-body session must never lock every muscle it touches.** The muscle-group rest gate (2026-07-23 remediation) is now per-muscle: `metrics._gates` reads `TrainingLoadMetrics.muscle_recovery`, which only records a muscle's rest clock resetting on a day it received `>= MEANINGFUL_DOSE_SETS` (4) primary-credited sets. *Why:* the prior group-level gate treated ANY single non-warmup set touching a group (push/pull/legs) as "the group trained today" — for an athlete whose sessions are distributed full-upper (every session touches both push and pull at 2–4 sets per muscle), this meant push and pull locked together after nearly every session, and on 2026-07-23 the intersection of that double-lock with the conditioning leg-hold (invariant 6's addendum) left only glutes legally trainable on an otherwise green day. `forbid_muscle_groups` is now DERIVED from per-muscle locks only when every muscle mapped to a group is individually locked (`MUSCLE_TO_GROUP`) — the partial case (e.g. chest locked, triceps free) no longer locks the whole group. Core (abs, lower_back) and forearms are not in `MUSCLE_TO_GROUP` and stay ungated, exactly as before this change — the remediation widens granularity, it does not newly restrict muscles that were previously free. The hip-hinge guard (#19 in `validate_plan`) is carried by EITHER the "pull" group or a rest-gated hamstrings/glutes/lower_back individually, so posterior-chain protection survives the granularity change without touching `muscle_group()`'s classification (invariant 4 untouched). Enforced by `test_distributed_full_upper_session_locks_no_muscle` / `test_distributed_full_upper_session_locks_nothing` (the exact collapse regression), `test_partial_group_lock_does_not_forbid_group`, `test_all_group_muscles_forbidden_derives_group`, and `test_muscle_rest_gate_blocks_hinge_via_individual_muscle` (test_gates.py / test_training_load.py / test_validate_plan.py).

9. **A movement never leads its head forever while an in-band alternative exists.** Rotation has two triggers: plateau, and tenure (`_ROTATE_AFTER_WEEKS` = 6 consecutive scored weeks). Both actuate only through `_in_band`, so a swap can relax lengthened→mid but never step into shortened, and never drops more than one SFR tier. *Why:* `_select_grounded` rotated on plateau alone, justified in-code as "(Balsalobre; Rauch): fixed selection matches or beats variation for hypertrophy." Both citations are inverted. The vault records Rauch 2017 as trained lifters choosing exercises per rep range **beating** fixed selection for upper-body strength and lean mass (`helms-2018-lv4-exercise-selection.md`), and Balsalobre as n=11 / 8 weeks / **no significant difference** in quad thickness. `exercise-selection-hypertrophy.md` prescribes rotation every 4–6 weeks for trained lifters, because hypertrophy is regional (Fonseca; Wakahara MRI) and the repeated bout effect extinguishes the EIMD stimulus within ~5 sessions of one movement; its "constrain variety" caveat is scoped to beginners' first 8–12 weeks. A progressing lift therefore led its head indefinitely — Face Pull took 34 of 73 prescribed plans. Enforced by `test_a_movement_never_leads_its_head_forever_when_an_alternative_exists`.

   **Known limitation, not yet an invariant:** rotation can only actuate where the candidate pool is deeper than the slot count. It is not. `exercise_science` holds 113 rows / 93 exercises against 738 exercise→muscle mappings; after dropping entries with no logged history and no alias resolution, **7 of 17 muscles have ≤4 usable candidates for 4 slots** (lower_back 1, calves 3, hamstrings 3, abs/adductors/forearms/traps 4), and six muscles are defined with a single region so the head-coverage pass has nothing to cover. Deepening that catalog is blocked on a provenance problem: **87 of 113 rows (77%) cite a source that appears nowhere in the vault** (Campos 2020, Yagiz 2022, Rodriguez-Ridao 2020, Maeo 2022 and 40 others), while the planner's own rule is "cite only real filenames from the VAULT CATALOG." Adding rows from an agent's recall would compound that. Curation must run from vault notes.

10. **Under-training is reachable only by an explicit, stated intent — never by absence, typo, or inference.** The maintenance tier (MV, migration 0078) is the one mechanism that deliberately holds a muscle BELOW its minimum effective volume, so every path that could apply it accidentally fails toward growth: a missing `tier` argument, a NULL/empty/unrecognised tier string, a pre-0078 schema where `volume_targets` falls back to the old query, and an emphasis muscle regardless of what the table says — all resolve to `'grow'`. Only the exact string `'maintain'` demotes. *Why:* the engine implemented 3 of the 4 volume landmarks its own cited source defines (`volume-landmarks-mev-mav-mrv.md`: "MV (~1–2 hard sets/muscle/week), MEV, MAV, MRV"). With MEV as the floor for all 17 muscles the weekly demand summed to **137 muscle-sets against ~94 deliverable** (63.5 working sets median × 1.48 primary+secondary credit) — so 16 of 17 muscles reported "below MEV" permanently, all 17 emitted ADD, and an unsatisfiable *unranked* list left the planner to triage silently toward whatever compounds were already habitual. That is the mechanism behind five rounds of "the engine keeps picking the same exercises": not a rotation failure, an absent priority model. But the fix's own shape — dropping a muscle from MEV to MV — is exactly what invariant 6 forbids a *fitted* band from doing, and is only legitimate as a human training decision. Safety branches (regressing, under-recovered, MRV, conditioning interference) are also evaluated BEFORE the tier, so maintenance removes volume *demand*, never recovery protection. Enforced by `test_maintenance_tier_is_explicit_only_and_never_reaches_an_emphasis_muscle` and `test_volume_targets_defaults_to_grow_on_a_pre_0078_schema`.

11. **Effort is part of the progression signal, and it may only ever demote a stall — never a rising e1RM, and never into a volume add.** `score_exercise` was built entirely from e1RM slope with a tonnage tiebreak, so *flat e1RM getting easier* and *flat e1RM costing more* both scored 3 ("stalled") and both got the same `+1 set` remedy — right for one, actively wrong for the other. With weekly per-exercise RPE materialised (migration 0079), a flat e1RM whose effort trend is **rising** ≥0.10 RPE/wk (and whose tonnage is not climbing) is re-read as regression. Two bounds are deliberate: (a) a **rising e1RM is never demoted on effort** — unambiguous progress whatever it cost, and demoting it would re-create invariant 6's anti-progression trap; (b) the **falling**-RPE case is deliberately NOT scored as progression, because perf ≥ 4 routes to `_decide`'s ramp branch and would add SETS, silently overriding the pre-existing `rpe_headroom` branch that argues the right thing for that exact case — a flat e1RM that keeps getting easier means the LOAD is too light. That signal goes to `_muscle_rpe_headroom` instead, which resolves per muscle rather than by the cross-muscle session average `plan_adherence` can offer. NULL RPE (≈87% of logged history) means "no effort claim" and scores identically to pre-0079. Enforced by `test_flat_e1rm_with_rising_rpe_reads_as_regression`, `test_rising_e1rm_is_never_demoted_by_effort`, `test_flat_e1rm_with_falling_rpe_does_not_become_a_volume_add`, `test_absent_rpe_scores_identically_to_pre_0079` (test_mesocycle_e1rm.py) and `test_per_muscle_rpe_headroom_reads_a_falling_effort_trend` (test_autoregulation.py).

12. **A classifier keyword matches a WORD, and a migration keys on identity — not on a column it is rewriting.** Two silent-corruption bugs of the same family. (a) `classify_exercise` tested `"chin" in name` as a bare substring, which also matches ma-CHIN-e: seven exercises / **2,155 logged sets** were classified as chin-ups — `Ab Crunch Machine` (744 sets) credited to lats instead of abs, and five overhead-press variants (1,402 sets) credited as **pulling**, which also reset the pull rest-gate clock on a push day. That is invariant 4's failure mode with the arrow reversed. Short tokens that can be embedded in a longer word now go through `_word()`; the guard also asserts the general property that adding "(Machine)" never changes an exercise's muscle. (b) Migration 0080 matched rows on `(exercise_name, citation)` while itself rewriting `citation`, and omitted `muscle` — so its re-grounding step overwrote the value its later drop step searched for, and one of three vault-contradicted rows (`Arnold Press (Dumbbell)` / side_delts) kept a citation pointing at the very note that refutes it. Row identity is `(exercise_name, muscle)`. *Why:* both bugs are invisible in aggregate — the volume table still balances, the catalogue still has rows — and both quietly train Rob according to the bug. Enforced by `test_substring_keywords_never_swallow_unrelated_exercise_names` (test_engine_invariants.py), `test_vault_contradicted_claims_are_not_selectable` and `test_no_curated_row_cites_an_unverifiable_paper` (test_exercise_science_coverage.py).

13. **e1RM is Epley over RIR-ADJUSTED reps, the adjustment fires only on evidence, and both e1RM paths share one expression.** Epley assumes the input set was taken to failure; Rob's best sets sit at RPE 7-8, so raw reps understate e1RM — and because the day's load ceiling is a *percentage* of e1RM, the understatement compounds into the prescription. Live case: Leg Extension 200×10 @RPE 8 logged 2026-07-23, then **175×10 prescribed at "RPE 8"** three days later — a plan claiming an effort its own load could not deliver, and the "treated like a fragile 40-year-old" failure (invariant 5) in a form invariant 5 does not catch, because the ceiling is legitimately capped on a yellow day; it was the *basis* that was wrong. `effective_reps = LEAST(reps + clamp(10 − rpe, 0, 3), 12)`. Three guards, all erring downward because this raises a SAFETY ceiling: a **missing RPE adds nothing** (~87% of history), **RIR credit caps at 3** so a very easy set cannot extrapolate far, and the **12-rep Epley cap binds AFTER the adjustment** (capping first would let a 12-rep RPE-7 set score as 15 effective reps, deep into the overestimate range the cap exists to prevent). Net effect ≈ +5%. *Why the first guard is load-bearing:* the initial implementation wrote `COALESCE(GREATEST(LEAST(10 - rpe, 3), 0), 0)`, which reads correctly and is wrong — DuckDB's LEAST/GREATEST **ignore** NULL arguments rather than propagating them, so `LEAST(10 - NULL, 3)` returns 3, the COALESCE never fired, and every RPE-less set silently took the full credit and inflated the ceiling. Both `mesocycle._CAPPED_E1RM` (progression) and `workout_planner.e1rm_by_exercise` (ceiling) route through `load_mechanics.effective_reps_sql`, so the engine cannot grade against one e1RM while prescribing off another. Enforced by `test_e1rm_never_inflates_on_a_set_with_no_logged_rpe` and `test_progression_and_ceiling_e1rm_share_one_expression`.

14. **The resistance ACWR arm measures fatigue, not just volume — and the fitter reads the same column the gate scores.** `v_daily_load`'s resistance component was raw volume-load (`weight x reps`). Tonnage is a good hypertrophy VOLUME metric and a poor FATIGUE metric, and this column is used as fatigue: `resistance_acwr` gates today's intensity. Raw tonnage inverts the ordering that matters — `3x5 @RPE 9` (15 reps of load) scored **below** `3x15 @RPE 6` (45 reps), so a shift toward heavier, lower-rep work read to the engine as *detraining* and was answered with more volume. Compounding: `v_session_load` correctly excludes powerlifting/weightlifting strain (lifting load belongs to this arm, not the HR arm), and beta-blockade suppresses HR on the conditioning arm — so on a propranolol day both arms of `composite_load` could understate effort at once. Sets are now weighted by RPE, the multiplicative form Foster's session-RPE uses, normalised at 7.0 so the Gabbett thresholds keep their meaning (they are defined on a ratio, scale-invariant within an arm). **A set with no logged RPE weights exactly 1.0** — ~98% of lifetime sets predate RPE logging, and the historical series the chronic window and every band fit read must move only on evidence. `hevy_tonnes` survives unchanged as the raw audit series, which creates a *column*-axis version of invariant 1's window-axis hazard: fitting a band on tonnage would fit a distribution the gate never produces. Live effect: resistance ACWR 0.83 → 0.88, conditioning and every gate unchanged. Enforced by `test_resistance_load_is_effort_weighted_and_history_is_untouched` and `test_acwr_band_fitter_never_fits_a_column_the_gate_does_not_score`.

15. **A capped day caps EFFORT, not load-as-a-fraction-of-1RM — so it can still prescribe a stimulating set.** `load_cap_pct` bounded load as a fraction of e1RM at a fixed rep count with **no reps-in-reserve term**, while an RPE target implies a load *with* one. Solving the two against each other (e1RM cancels) gives the highest RPE a day could prescribe while respecting its own ceiling: LOW(78%) → **−1.3** at 10 reps, MODERATE(90%) → **5.6**, HIGH(105%) → 11.9. The engine's own stimulating floor is RPE 6.0 (`volume._STIMULATING_RPE`), so a **MODERATE day could not prescribe a set its own volume model would count**, and on a **LOW day no such load existed at all** — while the planner prompt simultaneously demanded "working sets should land at RPE 7-8 ... do NOT default to a conservative RPE 6-7". The engine was asking for what its own validator forbade, and that is *also* why the load–RPE coherence check had to be scoped to HIGH days: HIGH was the only intensity where both constraints could hold. Live consequence: three successive revisions of the 2026-07-26 plan put 175, then 179, then 188 lb on Leg Extension, each labelled RPE 8, against a `200×10 @RPE 8` logged three days earlier — all three implied ~RPE 5. A reduced day in a hypertrophy block means **fewer hard sets, not easy ones**. Intensity now caps effort (`rpe_cap_for`: rest/deload 6, low 7, moderate 8, high 10), volume is modulated by the per-muscle set targets, and the load ceiling is DERIVED from the effort cap (`rpe_derived_ceiling_kg`) so a target at or below the cap is satisfiable by construction. HIGH is 10.0 and not 9.0 deliberately — a PR attempt against a stale e1RM is a genuine max effort and RPE 9 under-states it, so a lower cap would forbid the only honest label and freeze the strength ceiling (invariant 5). Coherence is consequently enforced on **every non-rest, non-deload day**, one-directionally: a load too LIGHT for its label is rejected, while a load implying RPE > 10 stays legal because that is what beating a stale e1RM looks like. Enforced by `test_a_capped_day_can_still_prescribe_a_stimulating_set`.

16. **A classifier keyword never decides a match by hiding inside a longer word.** Bare-substring matching has silently mis-classified twice: `"chin"` matched ma-CHIN-e (7 exercises / **2,155 logged sets** read as chin-ups — `Ab Crunch Machine` credited to lats, five overhead presses credited as PULLING and resetting the pull rest gate on a push day), and `"row"` matched ROWing Machine (a cardio movement that would credit lat volume the first time it is logged) and na-RROW Squat (correct today only because the squat branch runs first — by ordering, not by construction). Short tokens go through `_word()`, which is plural-tolerant because the catalogue mixes "Cable Rows" with "Bent Over Row" and a bare `\brow\b` would fail the same way in the opposite direction. Enforced by `test_no_classifier_token_decides_a_match_by_hiding_inside_a_longer_word`, which is a bug-FINDING test: it mines every keyword out of the classifier, obscures each hidden occurrence, and fails if the answer changes. Compound words where the hidden match is genuinely correct (`"skull"` in `"skullcrusher"`) sit in an explicit reviewed allowlist, so a NEW one forces a human decision instead of shipping silently.

17. **A migration writes to a base table, never a view.** DuckDB rejects `UPDATE`/`DELETE`/`INSERT` on a view — but only at RUN time, and migrations run at API startup, so the failure mode is the whole app refusing to boot. It happened twice in one day: 0080 wrote to `exercise_science` (a view over `exercise_muscle`) and took the API down; 0086 documented that lesson in its own header and then repeated it. Worse, DuckDB is not atomic across a multi-statement script, so statements before the failure have already committed, leaving the schema half-migrated with the version unrecorded. Enforced by `test_no_migration_writes_to_a_view`, scoped to 0067+ (0066 is where those objects became views; earlier migrations wrote to what were then base tables, ran successfully, and can never re-run).

18. **A reconciliation check recomputes; it does not re-run the code it checks.** `training/reconcile.py` exists because a green 719-test suite sat on top of a dozen live calculation defects — unit tests assert a function does what its author believed, and every defect that day was a belief that was wrong. Such checks only have that power while they derive expected values INDEPENDENTLY, from raw rows in plain SQL. A check that imports the helper it is checking becomes a tautology that passes forever and hides precisely what it was built to surface. `_e1rm_from_raw` is the reference for this discipline. Enforced by `test_reconciliation_checks_do_not_call_the_code_they_check`, which also asserts `run_all` reports a check that RAISED — a check that vanishes on error reads as clean.

## The rule for changing the engine

Any change to a gate, threshold, band-fit, volume decision, or classifier **must keep this suite green**, or must update an invariant *deliberately* — with the reasoning recorded here and in [DECISIONS.md](DECISIONS.md). "The test failed so I changed the assertion" is how the athlete gets quietly held back again. The test encodes the intent; the code serves it.
