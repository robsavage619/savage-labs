Run today's research cycle for the SHC Lab (the Savage Labs health app in __HOME__/Projects/savage-health-center). One specialist, then a blind methodologist, then (when a result is decisive) a blind devil's advocate, each a separate subagent. Never pass one subagent's reasoning to another.

## 0. Who is on today
The job runs once a week, on Monday, so the ISO week number picks the specialist (`date +%V`, read as a decimal number, then mod 4): 0 → hypertrophy, 1 → recovery, 2 → conditioning, 3 → metabolic. On any other day (a manual run): pick the specialist whose most recent notebook entry is oldest (GET http://localhost:8000/api/research/team, `last_activity`).

## 1. Check the Lab API is up
`curl -sf -m 5 http://localhost:8000/api/research/beliefs >/dev/null`. If it fails, the API is a launchd service that restarts itself: wait up to 2 minutes for the same curl to succeed, and if it still fails, stop and report "Lab API down, cycle skipped" with the error. Do nothing else in that case.

## 2. Specialist (subagent, model opus, effort high)
Spawn a general-purpose subagent with this brief, with <role> replaced by today's specialist:
"You are the SHC Lab <role> specialist. Read your full role instructions in __HOME__/.config/shc/agents/research-<role>.md and follow them exactly. The Lab API runs at http://localhost:8000 and accepts localhost requests without a key; use curl or python urllib. Start by reading your own agenda (GET /api/research/team) and the brief (GET /api/research/brief), including the other specialists' recent notebook entries: pick up their leads where they touch your field. The knowledge vault is read-only at __HOME__/.config/shc/vault; start at wiki/retrieval-pack-health-training.md and cite the note filename. This host has no literature search tools: cite vault notes only, propose no papers, and skip steps 2–4 of your role file's Literature section. If a question truly needs a paper the vault lacks, name the gap in your report instead. A day is in an arm when min <= value < max; `adjust` covariates are read on the exposure date. Body weight features are in pounds. Do not edit any repository file, run git, restart servers, or write to the database except through the research API routes your instructions name. Scratch files only in $TMPDIR. End by updating your agenda (PUT /api/research/team/<role>/agenda). The specialist may also write at most one `Experiment proposal:` notebook entry, design only, as its role file's Tier 3 describes, and any `Design gap:` explorations it finds. Return: explorations recorded, measurements proposed, formal questions proposed (slug, value, days to answer), beliefs added, and the single most interesting thing you found."

## 4. Run what was approved
If the methodologist approved or revised any question, `curl -s -X POST http://localhost:8000/api/research/run-all` so it has results today instead of waiting for the 04:50 nightly run.

## 4.5 Devil's advocate (separate subagent, model opus, effort high)
Pick the questions to challenge: from GET /api/research/hypotheses, active questions whose `result.verdict` is `supported`, `direction`, `against` or `ruled_out`, minus any already challenged at that verdict (GET /api/research/notebook?limit=500 has an entry with author `devils-advocate` and title ending `: <slug> at <verdict>`). Take at most 2, most recent `result.run_at` first; the rest wait for the next cycle. If none, skip this step.
For each, pass ONLY `id`, `slug`, `question`, `spec` and `result.verdict`. Never the effect, interval, rationale, or anything from the specialist's or methodologist's report. Spawn a general-purpose subagent with this brief, the picked questions appended as JSON:
"You are the SHC Lab devil's advocate. Read your full role instructions in __HOME__/.config/shc/agents/research-devils-advocate.md and follow them exactly: commit your threats to the notebook before you read any result, then read only the `result` block of your question. The Lab API runs at http://localhost:8000 and accepts localhost requests without a key. Do not edit files, run git, or restart servers. Scratch files only in $TMPDIR. Return: each slug, stands, qualified or doubtful, and the number that decided it."
Check that each challenged slug has both a `Pre-commitment:` entry and an outcome entry in the notebook, the pre-commitment written first. A missing or out-of-order pair is reported as a failed challenge, not a pass.

## 5. Verify, then report
Verify against the API, not the subagents' word: GET /api/research/team (the specialist's agenda changed), GET /api/research/hypotheses, GET /api/research/notebook?limit=20. Report in plain language, at most 12 lines: who ran, any new `Experiment proposal:` or `Design gap:` notebook titles (these wait on the subject, so they go near the top), what they explored and found (with numbers), what they proposed and why, the methodologist's calls, any new result (effect and 95% range), the devil's advocate's call on each challenged result (a `doubtful` one goes on the first line), current forecast skill for both targets (GET /api/research/forecast and /api/research/forecast?metric=strength_emphasis_pct14), and the experiment block scorer: GET http://localhost:8000/api/experiments/block, reporting whether it is `pending` and its weekly set counts so far (if the route fails, say so rather than skipping it). The 12-line cap does not apply to this scorer line.

Rules: never edit repository files, never commit or push, never touch the database except through the research API. The repository is public; nothing in this run writes to it.
